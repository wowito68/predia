Resumen

El presente reporte documenta la ampliación móvil de PREDIA, una plataforma clínica orientada a la gestión de expedientes y al apoyo para la detección temprana del riesgo de diabetes tipo 2. La solución web existente centraliza información de pacientes, consultas, signos vitales, recetas y predicciones de Inteligencia Artificial; sin embargo, su contexto principal de uso corresponde al escritorio y a sesiones clínicas prolongadas. La nueva integración móvil atiende necesidades diferentes: permitir al paciente consultar y registrar información de salud desde casa, y facilitar al médico la consulta y captura de datos durante rondas o atención al pie de cama.

La propuesta contempla dos roles diferenciados. El portal del paciente integra acceso a su resumen de salud, expediente en modo de lectura, citas, recetas, resultados de riesgo, automonitoreo y tendencias. La experiencia del médico prioriza agenda diaria, búsqueda rápida de pacientes, resumen clínico, alertas, registro de signos vitales, dictado de notas, captura de imágenes, validación de predicciones y firma de recetas. La aplicación se desarrolla con React Native y Expo, reutiliza la API de la plataforma web y mantiene autenticación, persistencia y control de acceso acordes con la naturaleza sensible de la información clínica.

Las dos primeras etapas abarcan el análisis de la brecha entre web y móvil, la definición de requisitos funcionales y no funcionales, el diseño de arquitectura e interfaces, y la construcción de un prototipo funcional conectado al backend de PREDIA. El resultado es una base móvil complementaria a la plataforma web, orientada a reducir tiempos de consulta, mejorar el seguimiento del paciente y acercar la información clínica al momento en que se requiere tomar una decisión.

Palabras clave: salud móvil, expediente clínico, React Native, atención clínica, automonitoreo, diabetes, Inteligencia Artificial.

Capítulo 1
Antecedentes

1.1 Tema del proyecto

PREDIA (Plataforma Clínica Inteligente para la Detección Temprana de Diabetes) es un proyecto de software clínico que integra la administración de pacientes, historiales médicos y herramientas de apoyo basadas en Inteligencia Artificial. Su propósito es organizar información clínica estructurada y convertirla en señales útiles para la prevención, el seguimiento y la toma de decisiones por parte de profesionales de la salud.

El proyecto original se implementó como una plataforma web con arquitectura cliente–servidor, API REST, base de datos relacional, autenticación mediante JSON Web Tokens y control de acceso por roles. Esta versión permite administrar pacientes, consultas, alergias, patologías, vacunas, antecedentes, signos vitales, documentos, recetas y predicciones de riesgo. La plataforma constituye el núcleo transaccional y clínico del sistema.

La evolución del proyecto incorpora una aplicación móvil complementaria. Esta nueva integración no pretende duplicar todos los módulos de la web, sino adaptar el producto a escenarios en los que el usuario necesita información inmediata, acciones breves y capacidades nativas del dispositivo.


Figura 1.1: Logo del proyecto PREDIA utilizado en la aplicación móvil.

El símbolo gráfico se construye a partir de una forma geométrica ascendente en color azul clínico. La composición comunica tecnología, precisión y evolución, mientras que la paleta azul se asocia con confianza, seguridad y atención sanitaria. El logo se utiliza como identificador visual común entre las experiencias web y móvil.

1.2 Contexto clínico y tecnológico

La diabetes mellitus tipo 2 representa un problema relevante de salud pública por su alta prevalencia, su evolución progresiva y el impacto de sus complicaciones. La detección tardía reduce las oportunidades de prevención y aumenta la necesidad de intervenciones complejas. Por esta razón, el seguimiento sistemático de factores como peso, índice de masa corporal, presión arterial, glucosa y antecedentes familiares resulta fundamental.

Al mismo tiempo, muchas instituciones y consultorios mantienen información clínica distribuida entre documentos físicos, hojas de cálculo y sistemas que no comparten datos. Esta fragmentación dificulta reconstruir la evolución del paciente, identificar valores anormales y dar continuidad al tratamiento. PREDIA surgió para centralizar esa información y utilizarla como base de un sistema de apoyo a la decisión clínica.

La adopción generalizada de teléfonos inteligentes abre un segundo contexto de uso. El paciente puede registrar mediciones fuera de la consulta y recibir recordatorios; el médico puede revisar datos durante una ronda, capturar una nota por voz o tomar una fotografía clínica sin depender de una estación de trabajo. Estas actividades requieren una experiencia diseñada para movilidad, interacción táctil, sesiones breves y conectividad variable.

1.3 Situación previa de PREDIA

Antes de la integración móvil, la plataforma resolvía principalmente el flujo del personal médico, de enfermería y administración desde navegador. El sistema ya contaba con base de datos clínica, endpoints de autenticación, pacientes, agenda, mediciones, recetas, documentos y predicciones. También existían mecanismos de seguridad, generación de reportes y contenedorización para el entorno de desarrollo.

No obstante, se identificaron cinco brechas principales:

1.
El paciente no disponía de una experiencia propia para consultar sus datos y participar en el seguimiento de su salud.
2.
La interfaz web no estaba optimizada para consulta rápida durante rondas o atención al pie de cama.
3.
La captura clínica móvil requería aprovechar micrófono, cámara y autenticación biométrica.
4.
El automonitoreo entre consultas no contaba con una interfaz específica para registro y visualización de tendencias.
5.
Los recordatorios y alertas dependían de mecanismos web o correo, con menor oportunidad que una notificación móvil nativa.

Estas brechas justifican una aplicación móvil especializada que consuma los servicios existentes, mantenga una fuente única de información y ofrezca funciones coherentes con el contexto del dispositivo.

1.4 Antecedente de requisitos móviles

El levantamiento previo definió 17 requisitos funcionales. Ocho corresponden al paciente: autenticación, dashboard personal, consulta de riesgo, expediente, recetas, citas, automonitoreo y tendencias. Nueve corresponden al médico: autenticación, agenda, resumen rápido, signos vitales, dictado, cámara clínica, validación de IA, alertas críticas y firma biométrica.

Los requisitos no funcionales consideran rendimiento, disponibilidad offline, protección de información, compatibilidad con Android e iOS, usabilidad, consumo de recursos y accesibilidad. Esta base permitió pasar de una idea general de “app móvil” a una arquitectura con roles, interfaces, prioridades y criterios de aceptación.

Capítulo 2
Definición del proyecto

2.1 Planteamiento del problema

La plataforma web de PREDIA centraliza información clínica y ofrece herramientas predictivas, pero no cubre por completo las necesidades que aparecen fuera del consultorio o de una computadora. El paciente continúa dependiendo del personal médico para conocer resultados, revisar indicaciones y dar seguimiento a sus mediciones. A su vez, el médico necesita acceder con rapidez al expediente mientras se desplaza, registrar signos vitales, documentar hallazgos y atender alertas sin completar flujos extensos diseñados para escritorio.

Esta separación entre la información disponible y el contexto real de uso provoca retrasos y fricción. Un dato de presión o glucosa registrado en casa puede quedar fuera del expediente; una alerta de alto riesgo puede no revisarse oportunamente; una nota clínica puede posponerse hasta que el médico regrese a una computadora. Además, la falta de participación directa del paciente limita la continuidad del seguimiento entre consultas.

El problema central consiste, por tanto, en que PREDIA dispone de información y servicios clínicos, pero requiere un canal móvil seguro y especializado que los acerque a dos momentos críticos: la autogestión cotidiana del paciente y la atención del médico en movimiento. Resolverlo exige mantener una sola fuente de datos, adaptar la navegación a tareas frecuentes y aprovechar capacidades nativas sin comprometer la confidencialidad del expediente.

La pregunta que orienta el proyecto es la siguiente: ¿cómo ampliar PREDIA mediante una aplicación móvil complementaria que permita al paciente participar en el seguimiento de su salud y al médico actuar con rapidez durante la atención clínica, conservando seguridad, trazabilidad y consistencia con la plataforma web?

2.2 Justificación

2.2.1 Valor para el paciente

La integración móvil mejora el acceso del paciente a información que le pertenece y que influye en sus decisiones cotidianas. Consultar citas, recetas, recomendaciones y tendencias desde un teléfono reduce dependencia administrativa y facilita la comprensión del propio estado de salud. El automonitoreo de glucosa, peso y presión permite construir una evolución más continua que la obtenida únicamente durante consultas periódicas.

2.2.2 Valor para el personal médico

Durante rondas y atención directa, la información crítica debe estar disponible con pocos pasos. Una vista rápida con alergias, medicamentos, signos recientes, riesgo y alertas reduce el tiempo dedicado a buscar datos dispersos. El registro móvil de mediciones, notas y fotografías disminuye la duplicidad de captura y mejora la oportunidad con la que la información llega al expediente.

2.2.3 Aprovechamiento de capacidades nativas

La aplicación móvil puede utilizar autenticación biométrica, cámara, micrófono y notificaciones. Estas capacidades permiten desbloqueo seguro, evidencia clínica, dictado de notas y avisos oportunos. Aunque algunas funciones podrían simularse en navegador, su integración nativa ofrece una experiencia más directa y adecuada para sesiones breves.

2.2.4 Reutilización de la inversión tecnológica

La solución no crea un backend independiente. La aplicación consume la API y la base de datos ya desarrolladas para la plataforma web, lo que reduce duplicidad y mantiene consistencia. React Native y Expo también reutilizan conocimientos del equipo en React, TypeScript, Zustand y TanStack Query. De esta forma, la ampliación móvil aprovecha la inversión previa y conserva una arquitectura mantenible.

2.2.5 Continuidad clínica y prevención

La combinación de información web y móvil permite registrar eventos en distintos momentos del proceso clínico. El médico genera indicaciones y valida riesgos; el paciente consulta esas indicaciones y aporta mediciones entre visitas. Esta continuidad fortalece el carácter preventivo de PREDIA y transforma la plataforma de un repositorio de información a una herramienta de seguimiento y apoyo a decisiones.

2.3 Alcances y restricciones

2.3.1 Alcances

El proyecto contempla los siguientes alcances para la integración móvil:

  • Aplicación multiplataforma desarrollada con React Native y Expo, con base común para Android, iOS y validación web del prototipo.

  • Autenticación diferenciada para médico y paciente, persistencia segura de sesión y base para desbloqueo biométrico.

  • Navegación médica mediante Inicio, Agenda, Pacientes, Alertas y Perfil.

  • Dashboard médico con citas del día, pacientes de alto riesgo, acciones rápidas y acceso al resumen clínico.

  • Resumen móvil del paciente con identidad, contacto, riesgo estratificado, alergias, signos vitales, consultas y recetas.

  • Registro rápido de signos vitales conectado a la API de PREDIA.

  • Dictado de notas con captura de audio, transcripción y persistencia de la nota en el expediente.

  • Captura de fotografías clínicas mediante cámara y flujo para adjuntar evidencia.

  • Revisión y validación de predicciones de Inteligencia Artificial por parte del médico.

  • Firma de recetas con autenticación biométrica cuando el dispositivo la soporte y flujo controlado de demostración en emulador.

  • Portal base del paciente con dashboard, expediente, recetas, citas, automonitoreo, resultados y tendencias.

  • Consumo de la API web mediante TanStack Query, manejo de estados de carga, error y refresco de datos.

  • Integración de objetivos de salud para peso, IMC y presión como base de seguimiento longitudinal.

2.3.2 Restricciones

Categoría

Restricción

Dispositivos

La validación funcional actual se ha realizado principalmente en Expo Web y emuladores; el comportamiento final de cámara, biometría, audio y notificaciones debe verificarse en equipos físicos Android e iOS.

Conectividad

La lectura y escritura clínica requieren acceso a la API. La estrategia offline completa, con cifrado local y cola de sincronización, permanece como trabajo posterior.

Notificaciones

La arquitectura contempla Expo Notifications, pero el envío push en producción requiere credenciales, configuración de proyectos y pruebas con servicios de Apple y Google.

Seguridad

La información médica exige protección de sesión, cifrado, control de permisos y cumplimiento normativo. El prototipo no sustituye una auditoría formal de seguridad ni una certificación clínica.

Interoperabilidad

La primera versión consume la API propia de PREDIA; no incorpora integración productiva con sistemas externos del IMSS, expedientes legados o redes hospitalarias.

Funciones pendientes

Mensajería clínica segura, QR/NFC, sincronización offline completa y recordatorios avanzados se encuentran fuera de las dos primeras etapas.

Modelo de IA

La predicción es una herramienta de cribado y apoyo. No constituye diagnóstico y requiere interpretación y validación médica.

Datos

El desempeño del modelo depende de la calidad y representatividad del conjunto de datos. Los resultados no deben generalizarse sin validación clínica externa.

Tiempo y recursos

El desarrollo se realiza en un contexto académico con un equipo limitado; las pruebas de campo, publicación en tiendas y operación 24/7 requieren recursos adicionales.

2.4 Objetivo general

Desarrollar e integrar una aplicación móvil complementaria a la plataforma web PREDIA que proporcione al paciente herramientas de consulta y automonitoreo, y al médico una experiencia de atención clínica en movilidad, mediante acceso seguro a la información, captura rápida de datos y aprovechamiento de capacidades nativas del dispositivo, manteniendo consistencia con el expediente clínico central y apoyo explicable a la toma de decisiones.

Capítulo 3
Desarrollo de las etapas

3.1 Primera etapa del proyecto

3.1.1 Análisis de la solución existente

La primera etapa inició con la revisión funcional de la plataforma web para identificar qué capacidades podían reutilizarse y cuáles requerían una experiencia móvil específica. Se analizaron autenticación, dashboard, agenda, pacientes, expedientes, consultas, recetas, mediciones y predicciones. El resultado confirmó que la web debía mantenerse como núcleo administrativo y clínico, mientras que la aplicación móvil debía centrarse en tareas breves y frecuentes.

Se documentó la diferencia entre ambos canales. La web está orientada a sesiones prolongadas, captura extensa y administración; la app móvil se enfoca en movimiento, consulta inmediata, automonitoreo, notificaciones y hardware del dispositivo. Esta decisión evitó construir una copia reducida del sitio web.

3.1.2 Definición de roles y requisitos

Se establecieron dos perfiles. El paciente requiere autogestión y consulta controlada; el médico requiere ronda clínica móvil. A partir de estos perfiles se consolidaron RF01 a RF17 y RNF01 a RNF07. Las prioridades altas se asignaron a autenticación, dashboard, expediente, recetas, citas, automonitoreo, agenda, resumen clínico, signos vitales, validación de IA, alertas y firma.

3.1.3 Arquitectura tecnológica

La arquitectura seleccionada utiliza React Native con Expo para compartir una base de código entre plataformas. React Navigation organiza flujos por rol; Zustand administra sesión; TanStack Query controla obtención, caché e invalidación de datos; SecureStore protege credenciales nativas; expo-local-authentication habilita biometría; expo-camera administra fotografías y expo-audio permite captura de voz.

La aplicación consume los endpoints existentes de Next.js. Para la integración desde entornos de desarrollo móvil se definieron variables de URL de API y políticas CORS. La persistencia continúa en MySQL mediante los servicios del backend, por lo que web y móvil leen la misma información clínica.

3.1.4 Diseño de interfaces y navegación

Se definieron mapas de interfaz por rol. El médico dispone de cinco pestañas inferiores: Inicio, Agenda, Pacientes, Alertas y Perfil. Desde el detalle del paciente se accede a signos vitales, nueva consulta por dictado, fotografía clínica, validación de IA y receta. El paciente dispone de una navegación centrada en su dashboard, expediente, recetas, citas, automonitoreo y tendencias.

Los criterios de diseño priorizaron jerarquía, contraste, lectura rápida y objetivos táctiles amplios. Las alertas y niveles de riesgo se comunican mediante etiquetas clínicas Bajo, Moderado, Alto y Muy Alto, evitando que una probabilidad numérica aislada sea interpretada como diagnóstico.

  • Objetivo general y objetivos específicos de la ampliación.

  • Diseño inicial de navegación y mockups de las pantallas principales.

3.2 Segunda etapa del proyecto

3.2.1 Construcción del proyecto móvil

En la segunda etapa se creó la aplicación Expo dentro del repositorio de PREDIA. Se configuraron TypeScript, alias de importación, React Navigation, TanStack Query y Zustand. También se establecieron recursos de aplicación, permisos para cámara y micrófono, iconografía y configuración para Android, iOS y web.

La aplicación comparte tipos y contratos con el proyecto principal cuando resulta viable, pero conserva componentes y pantallas propios para mantener una experiencia móvil. Los componentes reutilizables incluyen pantalla segura, encabezados, tarjetas, filas táctiles, estados vacíos, skeletons, avatares, indicadores de riesgo y botones de acción.

3.2.2 Integración de autenticación

Se implementó login diferenciado para médico y paciente. El médico utiliza las credenciales existentes de la plataforma; el paciente utiliza el flujo de identidad definido para la aplicación. En iOS y Android, la sesión se almacena mediante SecureStore y puede quedar pendiente de desbloqueo biométrico. En Expo Web se utiliza almacenamiento local como mecanismo de compatibilidad del prototipo.

La integración requirió habilitar preflight y encabezados CORS en la API para permitir consumo desde el servidor de desarrollo móvil. Además, se conserva un timeout de sesión como requisito de seguridad y se evita exponer datos clínicos antes de restaurar o validar la identidad.

3.2.3 Flujo del médico

El dashboard médico muestra citas del día, total de pacientes, alertas de alto riesgo y accesos rápidos. La agenda organiza citas próximas y permite abrir el paciente asociado. El directorio de pacientes incorpora búsqueda y acceso al resumen clínico.

La vista de paciente concentra datos básicos, contacto, riesgo, alergias, últimos signos, consultas y recetas. Desde ahí se puede llamar, abrir WhatsApp, registrar una nueva medición, iniciar una consulta por dictado, tomar una fotografía y generar una receta. Esta estructura reduce la navegación entre módulos independientes.

Los flujos clínicos conectados incluyen:

  • Registro de signos vitales y actualización del expediente.

  • Captura de audio, transcripción y guardado de la nota como consulta clínica.

  • Captura de fotografía con observaciones para evidencia clínica.

  • Revisión del nivel de riesgo, validación y registro de observaciones médicas.

  • Firma de receta con biometría cuando exista hardware compatible y alternativa controlada para demostración.

3.2.4 Flujo del paciente

Se construyó la base del portal móvil del paciente con pantallas de dashboard, expediente, recetas, citas, resultados, automonitoreo y tendencias. El dashboard presenta próxima cita, nivel de riesgo, indicadores y accesos frecuentes. El expediente se mantiene en modo de lectura para proteger la integridad de registros clínicos emitidos por profesionales.

El módulo de automonitoreo permite capturar glucosa, peso y presión; las tendencias organizan los datos en periodos para facilitar la lectura de evolución. Los objetivos de salud sirven como referencia visual y deben ser configurados o validados por el médico, no interpretados como prescripción automática.

3.2.5 Pruebas realizadas

La integración se verificó mediante compilación TypeScript y navegación automatizada en Expo Web con viewport móvil. Se probaron login, dashboard médico, agenda, pacientes, expediente, alertas y perfil, consumiendo datos reales de la API local. La prueba no reportó solicitudes fallidas ni excepciones JavaScript en el recorrido principal.

También se validó el backend local con autenticación, lectura de pacientes y persistencia de consultas. Las pruebas permitieron corregir CORS, restauración de sesión web, compatibilidad de Metro con Node 18, acciones sin comportamiento en perfil, persistencia de notas dictadas y bloqueo de firma en entornos sin biometría.

3.3 Resultado de las dos primeras etapas

Las dos primeras etapas permitieron transformar la integración móvil de una propuesta conceptual a un prototipo conectado con la plataforma clínica. La primera etapa redujo incertidumbre mediante requisitos, arquitectura y diseño por contexto. La segunda etapa comprobó que los servicios existentes podían reutilizarse y que los flujos prioritarios podían ejecutarse desde una interfaz móvil.

El principal resultado es una arquitectura de producto en la que la web y la app cumplen funciones complementarias. La web conserva gestión amplia, configuración y operación administrativa; la app acerca el expediente y las acciones clínicas al punto de atención, y abre un canal de participación para el paciente. Esta división evita duplicidad y proporciona una base realista para las siguientes etapas: offline seguro, push, mensajería, QR/NFC, pruebas en dispositivos físicos y piloto con usuarios.
